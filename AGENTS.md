# ChatHermes conventions

Use Vite+ (`vp`) for frontend linting, formatting, tests, and build workflows. Run `vp lint` and `vp fmt` for code quality; `npm test`, `npm run test:api`, and `npm run build` remain the project validation commands. Generated `plugin/chathermes/dashboard/dist/` assets are excluded from lint and formatting; generate them with `npm run build` for validation. Keep build output ignored; do not commit, stage, force-add, or push generated dist assets. **Never commit dist assets.**

ChatHermes is exclusively a Hermes dashboard plugin. Do not add standalone SPA, PWA, browser API keys, connection management, or direct cross-origin gateway requests. Vue mounts through the Hermes React plugin SDK; Python routes inherit dashboard authentication and keep gateway credentials on the server.

Keep the interface simple and compatible with the mobile ChatGPT reference images in `docs/internal/reference/chatgpt/`. Use quiet dark surfaces, readable text, a rounded composer, native profile and model selects, and slim thinking/tool disclosures. Active disclosures expand and show arriving data; completed disclosures collapse and remain available to inspect. Preserve the immediate sent-message → activity → assistant-response order.

The composer must stay focusable, including on the home screen and while requests are in flight. Gate sending separately. Keep all inputs and selects at least 16px to avoid iOS focus zoom. Suppress viewport zoom only while the plugin is mounted and restore host settings on unmount. File and camera attachments must travel through authenticated routes or supported image content parts.

Use Hermes's existing profiles, sessions, models, and agent runtime. Preserve cancellation and profile/session isolation. Follow the actual API contract of the pinned test version; model choices must affect the runtime, not only display labels. Never expose secrets in response bodies, errors, screenshots, or logs.

Use the layered environment documented in `tests/docker/README.md`. Build explicitly with `npm run test:env:build`; run real-Hermes deterministic contracts with `npm run test:integration` or `npm run test:integration:android`. Stock MockServer supplies inference through REST-loaded repository fixtures, without credentials or mounts. Compose owns infrastructure; browser preparation and optional Android installation are independent scripts. Test/setup failures must retain containers and state for agent debugging. Never add fixed readiness sleeps, coordinate-based setup controls, implicit reinstalls, automatic destructive resets, or cleanup-on-failure. Prefer observable user contracts to implementation-specific unit tests; retain focused protocol, security, deduplication, and pure-logic tests until replacements pass.

Use `docker compose --project-directory . -f tests/docker/compose.yml --profile android down -v` for explicit cleanup of only this project's resources. `COMPOSE_PROJECT_NAME` isolates concurrent environments; assign distinct published ports too. Real-provider tests are opt-in through `npm run live:real` and a separate project, using root `.env` provider settings. Never commit `.env`, credentials, generated Hermes state, or user session data.

Run `npm test`, `npm run test:api`, and `npm run build` for relevant changes. Keep generated `dashboard/dist/` assets out of commits. Always visually test changes in the actual dashboard plugin at mobile and desktop sizes before committing; inspect screenshots and check focus, scrolling, attachments, selects, and disclosure transitions. Document any test limitation honestly. Do not commit without that visual verification.

All Python development must use the repository's uv-managed Python 3.14+ environment. Run `uv sync --locked` to prepare it (or `uv sync` after intentional dependency changes). Manage development dependencies with `uv add --dev` and `uv remove --dev`; keep `pyproject.toml` and `uv.lock` synchronized. Do not use bare pip, manual venv creation/activation, or globally installed Python tools for development. Keep the plugin's metadata-only runtime dependency package separate from root development tooling.

After Python changes, run `uv run ruff format .`, `uv run ruff check --fix .`, and `uv run ty check`; resolve diagnostics before considering the work complete. Run relevant tests through `uv run pytest`. Use the reviewed Hermes source checkout at `.hermes-source` for ty imports and preserve the runtime test contract: `PYTHONPATH=.hermes-source:plugin uv run pytest`. See [developer setup](docs/developer/getting-started.md) for the exact source pin and [testing](docs/developer/testing.md) for CI checks and container-only probes.

Documentation starts at [docs/README.md](docs/README.md). Keep user tasks in `docs/user/` and developer guidance in `docs/developer/`; update the authoritative topic when behavior changes instead of duplicating details in the root README. Consult [architecture](docs/developer/architecture.md), the [API contract](docs/developer/api-contract.md), and [testing](docs/developer/testing.md) for current behavior. Preserve plans, verification records, and visual references under `docs/internal/` as historical evidence, not current setup instructions. Update relative links when moving documentation.
