# Issue #7 verification and limitations

## Outcome and upstream gap

Implemented everything supported by the inspected native contract: authenticated,
profile-local Project metadata browsing, Project selection, durable query URLs,
workspace availability errors, and existing conversations under Other chats.
Project New chat and sending fail closed. **This does not complete the full
Project-session requirements of #7.** No parallel membership store, path-based
classification, mobile IDs, context injection, or global active Project was added.

Source audit was repeated against the exact container pin
`3632f9173d218fd24f3fa595d7affa159b0774cd`, at
`/opt/data/profiles/developer/cache/scratch/hermes-pin-3632f917`. Native
in-process access was considered as well as REST/RPC. It does not supply the
missing relationship. The installed newer `/opt/hermes` also exposes no session
`project_id` contract in its schema/session store/API. No upstream revision
change was made.

Exact blockers in the pinned source:

- `hermes_state_common.py::SCHEMA_SQL` (sessions table) and
  `hermes_state_sessions.py::SessionSessionsMixin.create_session`: native sessions
  persist cwd and Git metadata, with no Project foreign key.
- `tui_gateway/project_tree.py::_project_for_session`: Desktop membership is
  computed from folder matches of cwd/repo root, rather than persisted.
- `gateway/platforms/api_server.py::APIServerAdapter._handle_create_session`:
  REST creation inserts only ID, source, model/model_config, system_prompt and
  started_at (then title); it ignores `project_id` and `cwd`.
- The same file's `APIServerAdapter._create_agent` does not pass saved session
  cwd as `cwd_override` when building the runtime. Inserting cwd through
  in-process `SessionDB` would not fix REST workspace/context initialization.
- Desktop's `tui_gateway/methods_session.py::_create_session` takes explicit cwd
  but no persisted Project association; `_resume_eager` restores cwd via
  `cwd_override`. The Desktop frontend
  `apps/desktop/src/app/session/hooks/use-session-actions/index.ts` passes cwd
  through `desktopSessionCreateParams` to `session.create`.

Full support needs an upstream persisted Project/session relationship, create
and list/detail contracts exposing it, runtime cwd initialization/resume, and
Desktop adoption. Successful Project grouping, Project-session creation,
Project-specific cwd/context inheritance, Project-session URL resume and
successful concurrent Project creates remain unimplemented for that reason.
They are not reported as passing tests.

## Files and native APIs reused

The existing branch's Project implementation lives in
`src/components/ProjectSidebar.vue`, `src/App.vue`,
`src/components/SessionSidebar.vue`, `src/types/hermes.ts`,
`src/lib/hermes-api.ts`, and `plugin/chathermes/dashboard/plugin_api.py`.
Cookie-authenticated plugin routes `/projects` and `/projects/{id}` adapt
`hermes_cli.projects_db.connect_closing/list_projects/get_project` and
`Project.to_dict`. Native metadata remains in each profile's `projects.db`.
The browser does not talk directly to the Bearer-only gateway.

Chats reuse the existing native SessionDB-backed `/api/sessions`, session detail,
messages, chat/stream and run cancellation routes through the plugin proxy.
Project/cwd creation fields are rejected with 501 before any gateway write.
No Project association is fabricated; cwd-lookalike chats remain ungrouped.
No initial Project working directory is set because Project creation is blocked.
Normal context discovery and precedence in
`agent/prompt_builder.py::build_context_files_prompt` remain untouched.

This follow-up changes:

- `tests/docker/init.py`: idempotent native seed for Hermes Mobile (available
  primary path), AcumaticaMCP (no primary path), Unavailable workspace (missing
  directory), plus native context files. Real keys remain in the environment;
  only synthetic fixture credentials are written to isolated profile files.
- `tests/docker/verify_seed.py`: verifies native IDs survive repeated startup,
  active Project is unchanged, path edge cases, and context precedence using
  Hermes's own prompt builder (no duplicate context parser).
- `tests/docker/Dockerfile`, `tests/docker/start.sh`, `compose.yml`,
  `.dockerignore`: self-contained pinned test image with plugin/config/scripts
  baked in, dedicated named data volume, no host bind mounts or personal home.
- `tests/docker/run.sh`: reproducible remote-Docker fixture/real modes,
  dedicated fixture network, environment-only real key forwarding, init process,
  and dashboard readiness wait. Fixture traffic uses container-name resolution;
  the supplied `172.25.0.1:14000` fixture address was unreachable in this daemon.
- `tests/integration/projects.mjs`: separate real integration, outside the
  normal Playwright suite; native Project routes, guarded Project create,
  native session create/stream, runtime model lock, UI resume/refresh/focus,
  and screenshots at desktop/mobile sizes.
- `src/App.vue`, `src/App.test.ts`, committed `dashboard/dist/` assets: remove
  secure-context-only `crypto.randomUUID` from render IDs. It threw on this HTTP
  LAN dashboard before the sent message/activity could render. Regression
  coverage exercises sending and tool activity with that API absent.
- `src/components/ProjectSidebar.vue`, `tests/visual/projects.spec.ts`: keep
  Project buttons at their natural touch height with a long chat list. Screenshot
  inspection found flex/grid compression clipping a Project name; the visual
  test now includes 21 chats and asserts every seeded Project button is at least
  48px high. The separate integration also checks button heights.
- `.gitignore`, `README.md`, `tests/docker/README.md`, source plan and this report:
  reproducibility, artifact locations, honest scope and upstream requirements.

## Real LiteLLM integration

`node tests/integration/projects.mjs` passed on the final rebuilt image at
1280 × 900 and 390 × 844. This run used the actual LiteLLM endpoint from inside
the Docker gateway; no browser route mocks or fixture model were used. In both
viewports:

- Anonymous Project access returned 401; dashboard form login supplied the
  existing session cookie for all authenticated plugin calls.
- Native Projects list/detail returned the seeded records and available primary
  path. Explicit Project/cwd session creation returned 501 before any write.
- Native session creation returned 201, chat/stream returned 200 and completed,
  and the runtime reported `gpt-6-luna` with `model_lock: confirmed` through the
  `Instant` route. The response was a real model reply, not the fixture string.
- The plugin resumed that exact session after navigation and refresh. Project
  selection/detail also survived refresh; the composer remained focusable.
- Each seeded Project button retained at least 48px height despite the long
  native chat list. Final screenshots were inspected at both sizes.

Native seed/context verification also passed in real mode and checked that the
real key was absent from the generated `.env`/config files. Native multi-profile
hosting activates whenever a second home exists, even with its config flag
false (`tui_gateway/launch_profile_policy.py::activate_multi_profile_hosting_eagerly`).
Real startup therefore removes only our seeded `test-profile` home and runs
single-profile with environment-injected credentials. Fixture startup recreates
the synthetic profile and validates profile isolation. Integration errors report
only a safe stage name because raw Playwright request exceptions include cookies.
