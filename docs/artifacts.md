# Files and artifacts

ChatHermes stages up to five files (20 MB each) in the authenticated dashboard plugin. The composer picker, camera picker, and chat-window drop target share `readAttachment` and the controller's `stage` action. Selecting files never submits a prompt. Failed reads/uploads retain the draft and successful attachments; select a failed file again to retry.

The native integration uses `image.attach_bytes` for supported raster images and `file.attach` with `data_url` for general files. Staged images are immediately detached. Only IDs for the selected profile and stored session are accepted by `chat.submit`; selected images are reattached immediately before `prompt.submit`, and native `ref_text` is preserved for general files. The existing model preflight, retained execution owner, cancellation, and uncertainty handling remain in use. Originals are preserved rather than resized by the browser.

`dashboard/artifacts.py` stores reference metadata in a profile-local SQLite index, with no duplicate file-byte store. Hermes messages are the source for submitted attachments and generated/tool artifacts. Discovery reads paginated history, including compaction ancestry, and includes only intentional transfers: user `Attached image …: /path` / `Attached file …: /path` markers (also written by submitted composer attachments), explicit user image content parts, and assistant/tool `MEDIA:/path` tags. Hermes desktop runtime identifies raw `MEDIA:` tags as explicit deliveries in `apps/desktop/src/app/artifacts/artifact-utils.ts`. Plain filesystem paths, Markdown links/images, `@file:` references, and structured output keys such as `output_path`, `saved_to`, or `file_path` do not establish a transfer. User mentions of `MEDIA:` never establish transfers. Staged, removed, or failed composer attachments remain excluded until submitted history contains their attachment markers. Session inline cards apply the same rules; tool arguments and thinking text do not attach generated files. Rediscovery revalidates cached index entries against history, hiding old heuristic discoveries while preserving upload metadata and deletion tombstones. Workspace-relative refs resolve against the stored session cwd. The index retains original upload names, sizes, direction, message/tool identity, timestamps, and deletion tombstones across navigation and restarts. A user asking for an output does not make that output an uploaded artifact.

The global drawer page and project Sessions / Chat → Artifacts tab both use `ArtifactBrowser`, `ArtifactAttachment`, `ArtifactPreview`, and the same service. Project membership comes from Hermes's project tree rather than guessed directory prefixes. Archived membership is resolved through native project session information. File cards expose names/types/sizes and conversation links; raster images, PDFs, text, and browser media can be previewed, while other formats download. Preview dialogs restore focus when closed.

Retrieval delegates to Hermes's authenticated filesystem download bridge, including its remote execution backend. Browser code never assumes gateway paths are browser URLs or reads a shared filesystem. Native sensitive-file, regular-file, and live-database guards are preserved. Previews use sandbox/CSP headers; active document formats such as HTML/SVG remain downloads.

The latest official Docker image restricts dashboard reads and managed deletion to `/opt/data`. Outputs outside that boundary remain indexed but native retrieval is denied. The visual suite generates its disposable output within `/opt/data` and reuses or creates an active native workspace project; a project-create conflict never skips verification.

Deletion requires confirmation and delegates to Hermes's managed-file deletion endpoint. The index is tombstoned only after the Hermes file is removed. The current native remote filesystem bridge has no deletion method: that operation returns an explicit unsupported response and keeps the artifact visible. There is no metadata-only deletion pretending to remove a Hermes file.

The visual artifact suite (`tests/visual/artifacts.spec.ts`) runs against the disposable real-provider dashboard at desktop and mobile sizes, covers staging/removal/drop, an actual tool-generated image, reload reconstruction, previews, download, confirmed deletion, and the shared project filter. `live-real.spec.ts` covers composer focus/scrolling, camera input, models, streaming, and disclosure transitions. API tests cover native staging, selected-image admission, profile/session boundaries, reconstruction/deduplication, project filters, native retrieval, and unsupported deletion. Files that Hermes cannot retrieve (for example an expired sandbox output) remain represented with a download action; their bytes cannot be recovered by ChatHermes.
