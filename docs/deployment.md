# Deployment

1. Run `npm ci && npm run build` and serve `dist/` as static files. Configure SPA fallback so `/p/<profile>/s/<session>` loads `index.html`.
2. Use a trusted single-user origin. HTTPS is recommended and required for a remote deployment and PWA installation. For local development, `npm run dev` serves the app on localhost.
3. Start Hermes with an API key for each intended profile. Add each connection in **Manage connections** with a label, base URL, and key. The base URL must be an API root such as `http://localhost:8642/`, or a shared multiplexer path such as `https://hermes.example.com/p/personal/`. Remote HTTP, URL credentials, query strings, and arbitrary paths are rejected. Each saved connection has its own key. Editing a profile may leave the key blank only when its normalized base URL stays the same; a different origin or multiplexer path requires a new key. Removing a profile removes its browser copy, not its Hermes sessions.
4. Configure Hermes or a trusted HTTPS reverse proxy to allow the exact ChatHermes origin with CORS. Permit `Authorization` and `Content-Type` headers and GET, POST, PATCH methods. Ensure preflight `OPTIONS` works. The installed Hermes gateway's CORS preflight currently omits PATCH, so cross-origin browser rename fails even though the PATCH route exists. To enable rename, update the upstream gateway CORS `allow_methods` to include PATCH, or have a trusted reverse proxy answer OPTIONS for `/api/sessions/{id}` with `Access-Control-Allow-Origin` set to the exact app origin, `Access-Control-Allow-Methods` including PATCH, and `Access-Control-Allow-Headers` including Authorization and Content-Type, then forward PATCH to Hermes. Verify the preflight in browser developer tools before using rename. The stream endpoint must expose SSE to cross-origin fetch. Redirects are rejected; configure the exact canonical base URL instead. An HTTPS app may be unable to reach local HTTP endpoints because of browser mixed-content or private-network rules, even when the URL is accepted by ChatHermes.

The browser sends `Authorization: Bearer <key>` directly to the pinned saved endpoint. API requests use `cache: no-store`, omit cookies, omit referrers, and use manual redirect handling. Keys are never placed in the URL or app logs. The service worker caches only the static shell, so uncached history and sending are unavailable offline.

**Security:** Browser `localStorage` exposes saved keys to any script running on the ChatHermes origin and to people with access to the browser profile or device. Use a trusted single-user origin and device; avoid third-party scripts and shared browser profiles. The Hermes key may authorize terminal-capable agent work. Keep keys out of build variables and static files. This client is not a multi-user authentication boundary.

The session API has not been exercised here with an authenticated live gateway. Before relying on it, use a disposable session to check list, create, history, stream, rename, named-profile routing, and source-specific continuation rules on your installed Hermes version. Navigating away aborts the browser stream but does not confirm a Hermes stop; check run or session status before retrying an uncertain turn.
