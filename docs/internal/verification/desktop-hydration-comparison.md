## Behavioral findings

### 1. REST selection, paging, mutation and identity

**Verified same — normal durable display selection and chronological order.** Both request latest 120 rows with `include_compacted=true`, include compression ancestors, and preserve server order rather than sorting by timestamp. ChatHermes: `hermes-api.ts:349–395`, `transcript.py:59–72`; Desktop: `api/sessions.ts:520–545`, `web_routers/sessions.py:751–777`. The common implementation is [`hermes_state_messages.py`](../../../.hermes-source/hermes_state_messages.py), lines 1370–1420: insertion/logical display order, newest-relative offset, chronological return order, indexed single-segment paging, and merged-lineage dedupe before slicing. Compaction copies prefer active/newer representatives but order by the logical first occurrence (1142–1190). This predates the attachment diff.

Concrete effect: pre-compaction conversations remain accessible; rewind-removed rows are not intentionally brought back merely because an ancestor retained a copy. Equal timestamp values do not justify a frontend sort. Relevant existing tests: `tests/transcript.test.py:35–85,235–291,383–402` and `tests/workflows/transcript.spec.ts:8,481`.

**Verified difference — ChatHermes adds revision-fenced pages.** `transcript.py:14–19,56–58,120–127` rejects mutation during/between reads, while `native-session.ts:149–179,188–229` retries conflicts, rejects non-advancing cursors, and invalidates stale backfill. Desktop's inspected REST route returns offset/order/returned counts without that revision contract (`web_routers/sessions.py:778–787`); it instead overlaps/grafts refresh pages (`resume-barrier-reread.ts:20–37`). Preserve ChatHermes's additional fence when aligning. Do not claim Desktop always mispages under mutation: overlap and reconciliation already mitigate several races, and no such failure was executed here. Predates current diff; tests at `tests/transcript.test.py:69,328,383` and `native-session.test.ts:1045,1090,1281`.

**Verified same, with a shared upstream limitation — text equality is not occurrence provenance.** The common display dedupe can collapse distinct physical appends with the same display identity; a changed clone without recognized lineage can appear in a different logical position. The explicit fixtures at `tests/transcript.test.py:253–291` compare the actual Desktop route and plugin: uncovered clones produce answers followed by newly placed prompts, and identical timestamp/content appends collapse. ChatHermes's normal history does not independently reorder this into alternating pairs. Desktop's row conversion additionally folds a tool turn into one assistant message and tracks `serverRowSpan` (`hydration.ts:344–348,388–392,603–630`); ChatHermes groups rows into one turn without changing upstream row offset counts (`transcript-entries.ts:71–101`, `native-session.ts:220–223`). This is not repaired by hiding attachment context and predates the diff.

**Verified difference — legacy full-history resource protection.** Both reject an orderless “latest” page as a trustworthy tail: ChatHermes `hermes-api.ts:370–378`; Desktop `api/sessions.ts:548–559,585–609`. Both then use oldest-page reads when needed. Desktop bounds that complete load at 32,000,000 JSON characters (`api/sessions.ts:675–702`); ChatHermes has repeated-page/non-advance checks and ID dedup but no equivalent aggregate JSON cap in its loop (`hermes-api.ts:398–449`). A large legacy transcript can therefore consume more browser memory in ChatHermes. The exact latency/OOM threshold is **unknown**. Predates current diff.

**Unknown — a 120-row response does not prove bounded total server work.** Both use the same multi-ancestor branch that materializes merged payloads before paging (`hermes_state_messages.py:1387–1398`). ChatHermes also computes revision stamps. Existing `tests/transcript.test.py:149–176,294–326` explicitly distinguishes selected payloads from multi-rotation work. No new timings or memory measurements were taken. Neither frontend can promise constant-cost reads for arbitrarily long compression lineages at this pin.

### 2. Native resume and in-flight reconciliation

**Verified same — REST is normally the durable transcript authority; native resume supplies live state.** Both use deferred/omitted-history resume and retain REST tools/attachments rather than treating a compact native snapshot as a complete archival transcript. ChatHermes `native-gateway.ts:249–295`, `native-session.ts:332–408,423–444`; Desktop `resume-owner.ts:107–131`, `index.ts:2087–2147`. Upstream [`session_registry.py`](../../../.hermes-source/tui_gateway/session_registry.py), lines 790–829, takes in-flight/queue/running state under the history lock, skips the DB history read for omitted messages, and includes open requests. Native history is deliberately lossy for ordinary tool outputs: [`session_history.py`](../../../.hermes-source/tui_gateway/session_history.py), lines 333–345, sends an 80-character context plus args/labels and original result bodies only for selected edit tools. Neither app can reconstruct every historical tool result from that RPC alone. Predates diff.

**Verified difference — initial scheduling and fallback.** Desktop overlaps prefetch/resume and has a REST fallback if resume fails (`index.ts:1985–2024,2373–2408`). ChatHermes initiates `hydrate()` after recovered state becomes ready (`native-session.ts:860–886`); hydration itself returns early unless the viewer is ready (409–413). Thus a fresh ChatHermes open whose native reconstruction fails has no independent REST-only opening path there, while an already visible transcript is retained read-only. This can delay the first durable paint by transport/resume work and can leave cold history unavailable when the native connection fails although REST would work. It is a verified control-flow difference, **not** a measured latency or reproduced outage. Predates diff. Existing reconnect tests cover retained history/retry (`native-reconnect.test.ts:365–451`), not full equivalence with Desktop's cold REST fallback.

**Verified same in intent, different mechanisms — prevent stale snapshot/final duplication.** ChatHermes holds frames during native reconstruction, confirms running state once with activation, stages Vue updates, then hydrates (`native-gateway.ts:263–302`; `native-session.ts:730–755,860–873`). Desktop uses replay barriers, newer-row checks and settled-live preservation (`resume-barrier-reread.ts:40–110`; `resume-reconcile.ts:1–66`; `index.ts:2075–2147`). ChatHermes preserves live suffixes during delayed REST, uses durable receipts where available, and does not retire a projection on a partial write (`native-session.ts:485–628`). Existing tests target these race shapes: `native-session.test.ts:1118–1390`, `tests/workflows/transcript.spec.ts:227`, Desktop `reconnect-resume-barrier.test.tsx`, `warm-resume-replay-barrier.test.tsx`, and `use-message-stream/gateway-event/settled-during-resume.test.ts`. Universal exactly-once recovery is **unknown**, not established by those mechanisms.

**Verified same — partial persisted commentary and Unicode correction offsets have guarded recovery.** ChatHermes [`persisted-live-turn.ts`](../../../src/features/chat/runtime/persisted-live-turn.ts), lines 8–35 and 58–109, mirrors Desktop [`use-session-actions/persisted-live-turn.ts`](../../../.hermes-source/apps/desktop/src/app/session/hooks/use-session-actions/persisted-live-turn.ts), lines 28–121,141–189,197–299: seek a source-addressed partial turn, stop at a saved final, match correction sequence, subtract only represented prefix text, and use Python code points rather than UTF-16 offsets. Invalid/missing offsets cannot recover a trustworthy phase split. ChatHermes explicitly stringifies multipart input in this heuristic (38–52); this does not prove matching attachment identity. Existing tests: ChatHermes `persisted-live-turn.test.ts`, `native-session.test.ts:1212,1255,1304`; real steering workflow `transcript.spec.ts:552`. Predates diff; semantic parity across every Desktop part shape remains **unknown**.

**Verified difference — Desktop verifies painted source coverage before subtracting a partial prefix.** Desktop’s partial-turn candidate checks that the prompt/corrections are present as rendered durable rows and that each nonempty assistant commentary row has a matching rendered text part carrying its exact `sourceRowId` (`use-session-actions/persisted-live-turn.ts:34–78`). ChatHermes’s candidate checks row IDs and raw source shape but has no equivalent rendered-part provenance check (`persisted-live-turn.ts:58–109`); it later rebuilds raw history blocks and subtracts the represented prefix (`native-session.ts:487–530`). This distinction matters when display projection, media conversion or folding changes text: equal raw prefix text is a weaker coverage test than an actually painted source-addressed part. The basic correction/prefix algorithm is shared, but full reconciliation parity is not verified. This predates the attachment diff. Add fixtures where raw, projected and rendered commentary differ, asserting that no unseen prefix is subtracted.

**Verified difference — crash-survivable local progress.** Desktop persists a bounded, throttled in-flight tail to localStorage and recovers it into durable history (`lib/inflight-turn-journal.ts:15–49,1051–1081`; main `index.ts:2180–2197,2394–2403`). ChatHermes's projection is held in the native session owner (`native-session.ts:332–408,675–705`); its localStorage use in [`native-admission.ts`](../../../src/features/chat/runtime/native-admission.ts), lines 1–42, records ambiguous admission locks, not a text/tool journal. Reload can recover server snapshots and persisted REST rows, but cannot use a local journal to recover richer unpersisted parts the server no longer retains. Predates diff. Adding a journal trades recovery against storing sensitive transcript text in browser storage; Desktop's bounds/expiry are not a reason to copy it without profile and deletion design.

**Unknown / upstream cannot guarantee — replay provenance.** ChatHermes synthesizes `recovery: {epoch: "native-snapshot", through: 0, base_row_ids: null, complete: false}` (`native-gateway.ts:289–295`); its later sequence is client-local (304–310), and reconciliation confirmation compares a local boundary with current idle state (360–367). These are not a server-issued durable event cursor or persisted occurrence receipt. Upstream in-flight snapshots expose flattened assistant text, correction offsets and optional errors, not the complete tool/thinking timeline (`session_auto_continue.py:528–555`). Desktop's prefix matching/journal also cannot invent missing provenance. A disconnected client may lose transient tools/thinking, and repeated equal prompts remain ambiguous without stronger source identity. Do not advertise exhaustive replay, idempotent re-submission, or lossless crash recovery at this pin.

### 3. Roles, hidden rows, notices, compaction and legacy data

**Verified same — ordinary hidden scaffolding is excluded from visible history.** ChatHermes `transcript.py:116–118`, `gateway-display.ts:16–20`, `transcript-entries.ts:14–18`; Desktop `hydration.ts:162–171,502–508`. Upstream REST hides untyped reserved `[System:` user scaffolds and recovers typed failures, steer text and withheld prompts (`web_routers/sessions.py:657–740`). Native history filters unsupported roles, explicit hidden rows, marker scaffolds and projects skill invocations (`session_history.py:305–371`). Consequently missing ChatHermes frontend string checks do **not** establish that normal pinned server history exposes all scaffolds.

**Verified same for normal REST model-only filtering; verified defensive difference for alternate input.** Desktop explicitly filters `display_metadata.model_only === true`, parsing legacy JSON metadata (`hydration.ts:192–212,458–459`); ChatHermes `gateway-display.ts:16–20` does not. However both normal compacted REST reads already exclude model-only rows in the common DB display selection (`hermes_state_messages.py:1119–1121,1179–1180,1327–1341`). Therefore “ChatHermes visibly leaks merged prompts on normal REST hydration” is **not verified**. A directly supplied/raw/older native row that survives upstream filtering would be accepted differently by the clients; add defensive parsing without removing current server protection. Predates diff. Desktop has `chat-messages/hydration-model-only.test.ts`; add a corresponding ChatHermes observable history fixture plus a protocol-focused fallback test.

**Verified difference — plain system rows and legacy heartbeat fallback.** ChatHermes hides unrecognized `role=system` rows but recognizes known `display_kind` values as status first (`gateway-display.ts:16–20`). Desktop retains ordinary nonempty system rows for its system renderer and hides legacy heartbeat-shaped user rows without a kind (`hydration.ts:30–34,162–171,508,657–671`; `system-message.tsx:119–189`). The native server itself hides several reserved markers and infers kinds (`session_history.py:228–283,318–329,367–369`), so reachability depends on REST/native route and producer vintage. For an untyped heartbeat row delivered through REST, Desktop's frontend suppression is additional protection; for an ordinary system notice, ChatHermes drops information Desktop can display. Predates diff; exact historical database prevalence is **unknown**.

**Verified difference — notice detail and error presentation.** Both have typed model/personality/auto-continue/background/failure notices. ChatHermes uses labels/`display_text`, renders delegation completion as completed work holding the original receipt, and otherwise offers original status content (`gateway-display.ts:4–35`; `transcript-entries.ts:31–58`; `ChatTranscript.vue:213–250`). Desktop makes them system messages, extracts async/process result bodies, supports task counts, and renders result detail through Markdown or log viewers (`hydration.ts:178–189,231–245,277–337,638–665`; `system-message.tsx:21–87`). ChatHermes does not extract the same producer-owned result envelope, so inspection can show more orchestration text rather than just task output. Predates diff; there is existing live batch coverage at `native-session.test.ts:846`, but no comprehensive cross-client notice-rendering matrix.

**Verified same — pure compaction handoffs are not ordinary user prompts; authentic embedded asks may survive.** Both call upstream compaction display projection: `transcript.py:70–72` → `web_routers/sessions.py:725–740`; native `session_history.py:308–310`; implementation [`compaction_display.py`](../../../.hermes-source/agent/compaction_display.py), lines 33–54. A pure handoff becomes hidden/absent; a recoverable real ask becomes display content. ChatHermes's support for an explicit `display_kind=compaction` divider (`gateway-display.ts:17`; `transcript-entries.ts:26–29`) does not mean normal pinned history emits that divider. Tests deliberately establish no invented marker (`tests/transcript.test.py:107–147`). Predates diff.

**Unknown — internal sidecars on recovered compaction carriers need a focused fixture.** Native compaction projection removes inherited tool/reasoning/provider internals (`compaction_display.py:10–29,46–53`); REST keeps the physical row and adds `display_content` (`web_routers/sessions.py:728–738`). Both frontend conversions can read reasoning alongside display text. It is not established here that a selected representative containing a recovered ask also carries inappropriate reasoning through these paths. Do not assert a visible leak from this asymmetry without generating the actual carrier and tracing the chosen representative. This is an upstream-route parity test candidate, not an attachment regression.

**Verified difference — malformed and legacy input tolerance.** Common DB decoding already normalizes content/tool-call JSON/metadata and drops unknown binary columns (`hermes_state_messages.py:1297–1319`). Native history skips non-dict/unsupported-role rows (`session_history.py:305–313`). Desktop additionally handles malformed JSON metadata and provider sidecars in hydration (`hydration.ts:63–123,192–205`), and supports `content/text/context/name` fallbacks (497–500). ChatHermes rejects an entire REST page if a row lacks a string role (`hermes-api.ts:99–117`), returns empty text for unsupported object content (`453–466`), and iterates expected tool-call arrays in `assistant-turn.ts:267–276`. It does not implement Desktop's full defensive conversion. Valid server-normalized rows are not thereby broken; malformed remote/legacy/tool shapes can differ or fail. Predates diff. Whole-app failure from any particular malformed row is **unverified**; add route-realistic malformed fixtures rather than speculative catches.

### 4. Commentary, thinking, tools and display metadata

**Verified difference — projected assistant detail is lost in ChatHermes's normal REST path.** Upstream [`history_commentary.py`](../../../.hermes-source/agent/history_commentary.py), lines 117–154 and 157–180, creates policy-scoped `display_commentary` and `display_reasoning`, strips public commentary from the display reasoning copy, and sanitizes relevant display content. Desktop uses those fields and has a final-answer-only provider-sidecar fallback (`hydration.ts:59–123,529–559`), plus `reasoning_details` fallback (534–540). ChatHermes's allowlist omits `display_commentary`, `display_reasoning`, `reasoning_details`, and `codex_message_items` (`transcript.py:73–88`); its history converter only reads raw `reasoning_content || reasoning` and canonical/display content (`assistant-turn.ts:241–251`). It also does not consume the projected commentary fields on native restored rows.

Concrete conditional effects: a public commentary item existing only in its approved projection disappears after cold hydration; commentary flattened into raw reasoning can remain in ChatHermes's thinking disclosure instead of being removed by `display_reasoning`; a final existing only in an allowed provider sidecar can lack Desktop's fallback; reasoning-details-only history loses its thought. Canonical content that upstream already projected still benefits from `display_content`; do **not** infer all commentary or all answers are missing. This predates current diff and is the most substantive metadata alignment gap. Existing `tests/transcript.test.py:350–380` checks raw reasoning/tools but not these projected fields. Desktop has `chat-messages.codex-commentary-reprojection.test.ts`, `chat-messages.codex-sidecar-hydration.test.ts`, `chat-messages.codex-json-sidecar.test.ts`, and `chat-messages.interim-preservation.test.ts`. No runtime reproduction or secret-disclosure finding is claimed here.

**Verified same — baseline reasoning, calls, results and chronological phases survive ordinary REST hydration.** ChatHermes `assistant-turn.ts:233–302` creates separate saved text phases, retains reasoning and call IDs, detects several result failure forms, and updates matching tool calls; Desktop `hydration.ts:468–490,534–568,603–630` and [`tool-parts.ts`](../../../.hermes-source/apps/desktop/src/lib/chat-messages/tool-parts.ts), lines 1033–1168, perform part-level result attachment and folding. The common REST projection supplies tool labels (`web_routers/sessions.py:634–636,705`), and both preserve authored assistant text before/after tool activity. Existing tests: `tests/transcript.test.py:350`, `assistant-turn.test.ts`, `transcript-entries.test.ts`, Desktop `chat-messages.test.ts` and `chat-messages.stopped-tool-fold.test.ts`. This is not proof of every provider tool shape.

**Verified difference — richer Desktop tool and interaction metadata.** Desktop consumes stored labels, reactions, interruption marks, durable completion, source row IDs and unique call IDs (`hydration.ts:243–273,525–575,638–688`). ChatHermes's server carries some of these fields, including `tool_call_labels`, but the history block conversion does not apply the labels or reactions/interrupted/error-surface metadata (`transcript.py:73–88`; `assistant-turn.ts:241–298`). Desktop renders todo state separately, specialized clarify/delegate/image/setup/theme/connector cards, and display-preference-controlled generic activity (`message-parts.tsx:124–194`). ChatHermes uses generic activity disclosures and artifact results (`TurnWork.vue:44–76`; `ActivityRow.vue:72–104`; `AssistantTurn.vue:122–139`). A reloaded Desktop session can retain more semantic tool UI and stopped state; ChatHermes may show a generic call/result or only a failure notice. Keep ChatHermes's simple UI, but preserve the meaning and identity needed for safe inspection. Predates diff; specialized-card parity is not a realistic requirement for the first alignment pass.

**Verified difference — persisted failures and live errors.** Desktop converts a `failed_turn` metadata error surface into an assistant error card plus a separate system boundary (`hydration.ts:214–229,638–650`), and its assistant renderer consumes structured error metadata (`thread/assistant-message.tsx:571–598`). ChatHermes treats that row as a status notice and does not reconstruct the structured card (`gateway-display.ts:10,16–20`; `transcript-entries.ts:52–58`). It restores in-flight error text and live generic errors (`native-session.ts:399–405,783–786,824–830`), but not Desktop's full error-surface recovery actions. Effect: a saved failed turn can reopen with less diagnosis/recovery detail than Desktop. Predates diff. Test with actual failed boundary metadata and retained partial output, not only a live error string.

### 5. Attachments, context, warnings, references and images

**Verified difference — current diff changes file-context presentation and response matching.** In base, `uploadedArtifacts` parsed the entire text without removing native appended context; only saved-response matching had a narrow `\n@file:...\n\n--- Attached Context ---` suffix regex. Current `artifacts.ts:473–479` calls [`attached-context.ts`](../../../src/features/artifacts/attached-context.ts), lines 1–104, before discovering upload cards, and `saved-response-targets.ts:8–10` shares that same visible projection. The parser requires a prior upload, a top-level marker and complete recognized file blocks tied to upload/staged paths. Warnings remain visible; unsupported or budget-exhausting input remains visible. Shared scan budget is 1,000,000 characters plus per-preview state/fence caps (16–56,66–103). Expanded file contents are no longer scanned to manufacture downloads when the suffix is recognized. This fixes an attachment-specific presentation/matching discrepancy relative to base, while intentionally retaining stricter authored-text preservation than Desktop.

Desktop `hydration.ts:30–36,126–159` truncates **any user text** at the first matching attached-context marker and hoists unique `@file/@folder/@url/@image/@tool/@terminal` references from the suffix when missing from visible prose. There is no corresponding prior-upload or complete-envelope requirement. Example: authored `Explain this heading:\n\n--- Attached Context ---\n\nThis is my own text about @file:example.pdf` loses the author's suffix and gains a hoisted reference in Desktop; current ChatHermes preserves it. The new `desktop-attached-context.test.ts:28–33` explicitly captures this tradeoff. Do not copy marker truncation wholesale to achieve parity.

**Verified difference — warnings and reference breadth.** Upstream leaves references in authored text, then appends warnings before attached context (`agent/context_references.py:241–250`); soft/hard injection thresholds are 25%/50% (215–239), and hard refusal returns without an appended context body. Desktop strips a matching warnings section even without attached context (`hydration.ts:144–150`). Current ChatHermes retains warnings verbatim, including multiline exception continuations (`attached-context.ts:78–103`), and only hides recognized file expansions. Desktop's generic reference renderer turns supported directives into chips/thumbnails (`directive-text.tsx:119–130,348–382`; `user-message.tsx:561–587`); ChatHermes upload parsing is a narrower authenticated artifact-delivery vocabulary (`artifacts.ts:350–416,473–518`; `UserMessage.vue:15–31`). Folder/URL/tool/terminal context or a plain authored `@file` does not imply a plugin-managed downloadable upload. General reference UI breadth predates diff; strict footer hiding and warning preservation are current-diff choices. Neither client can guarantee a referenced file still exists or that historical external content is retrievable.

**Verified same — presentation filtering does not remove model context.** ChatHermes's current parser runs in the browser; its server keeps the expanded context content and routes through upstream projection (`transcript.py:70–99`). Desktop's truncation is likewise frontend display conversion (`hydration.ts:126–159`), after upstream persistence. Current `tests/transcript.test.py:437–499` calls the actual pinned context producer, verifies binary/warning placement and retained SQLite/history content, and tests cross-profile rejection. That test was inspected, not executed. The new browser comparison executes an extracted Desktop display helper with stubbed dependencies (`desktop-attached-context.test.ts:8–26`); it is **not** proof of complete Desktop hydration/rendering or Desktop attachment transport.

**Verified difference — inline-image transport and runtime reference handling.** Desktop REST does not override `inline_images` (`api/sessions.ts:473–509`; upstream default `web_routers/sessions.py:744–747`), and Desktop also recognizes persisted image-routing suffixes, lifts image refs and leading attachment refs (`hydration.ts:38–49,510–522`). ChatHermes asks for `inline_images=false` in the URL but its `transcript=1` handler intentionally projects with `inline_images=True`, then rewrites data-image parts to authenticated row addresses (`transcript.py:70–72,100–115`). Thus the normal plugin path does **not** simply turn every image into `[image]` because of that query parameter. Its image handler rechecks session lineage and visibility (`transcript.py:141–176`). Browser rendering accepts those addresses, supported data/HTTP image URLs, and mapped plugin upload originals (`message-image.ts:1–9`; `artifacts.ts:481–518`; `assistant-turn.ts:253–265`). This keeps normal image bytes out of the transcript HTTP response, though server projection still processes the source data. Predates diff.

Desktop consumes image references via `DirectiveContent` and image components (`directive-text.tsx:348–382`; `user-message.tsx:571–587`); ChatHermes renders authenticated artifact cards and its user prose replaces screenshot placeholders globally (`UserMessage.vue:19–31`). A literal authored `[screenshot]` can therefore be relabeled in ChatHermes, while Desktop's persisted-image special case requires a matching suffix count (`hydration.ts:40–49`). Desktop also deduplicates generated-image echoes and repeated assistant part text (`hydration.ts:678–688`); ChatHermes's artifact-path dedup is a different scope (`AssistantTurn.vue:98–139`). Arbitrary Desktop image/path compatibility, expired files, remote filesystem access and identical thumbnail output are **unknown**, not guaranteed by upload parity. Existing `tests/transcript.test.py:178–233`, `tests/workflows/transcript.spec.ts:435`, and `tests/visual/image-preview-live.spec.ts` cover relevant plugin cases.
